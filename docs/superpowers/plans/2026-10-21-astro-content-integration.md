# Astro Content Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the template-local Astro content helper with a reusable in-repo `orso-astro` integration, copied into every scaffolded project, and switch the daemon's catalog and save paths to the integration's manifest and dev-only endpoint.

**Architecture:** `packages/astro/` is a real ESM package named `orso-astro` with no build step. It wraps Astro's `glob()` loader with `orsoGlob()`, reads `src/content.config.ts` through the Vite runner during `astro:server:setup`, writes `.astro/orso-content.json`, and mounts `POST /__orso` when `ORSO_CONTENT_TOKEN` is set. The Rust daemon reads the manifest for collection metadata and calls the endpoint for schema validation and source-preserving patches. Scaffolded projects embed a copy of the package at `packages/astro/` and rewrite the local dependency path so they remain self-contained. The legacy helper and its Zig-like registry are removed only after the save path no longer needs them.

**Tech Stack:** Astro 7.3.5, Zod 4.5.4 (`astro/zod`), Node ESM, `yaml`, `js-yaml`, `jsonc-parser`, Vite dev-server middleware, Rust/Axum/Reqwest, Vue/Pinia, `node:test`, Vitest, Cargo integration tests.

**Spec:** `docs/superpowers/specs/2026-10-21-astro-content-integration-design.md`

---

## Sequencing Decision

The design's first delivery slice says to delete the template helper immediately. This plan keeps
`templates/astro-marketing/scripts/orso-content.mjs`,
`templates/astro-marketing/scripts/orso-content.test.mjs` and
`templates/astro-marketing/src/content-schemas.mjs` until **Slice 3, Task 14**, after the Rust save
and lifecycle paths have switched to the HTTP endpoint.

Reason: through Slice 2 the Rust mutation/lifecycle code still calls the helper's `patch` operation.
Deleting it in Slice 1 or 2 would leave the content tests red until Slice 3. The new template config
uses `orsoGlob()` from the package immediately; the old helper is simply unused by the new config
during the transition. Task 14 removes the legacy files, tests and dependencies. The final state is
exactly the approved design.

Every completed task leaves `cargo test`, `npm --prefix packages/astro test` and
`npm --prefix templates/astro-marketing test` green unless a task explicitly says it is a
test-fixture-only transition.

## Global Constraints

- Package name: `orso-astro`; source at `packages/astro/`; ESM; no build step.
- Package runtime dependencies: `yaml`, `js-yaml`, `jsonc-parser`.
- Package peer dependency: `astro >=7.3.0 <8`; package tests use `astro@7.3.5` as a dev dependency.
- Template dependency: `"orso-astro": "file:../../packages/astro"`.
- Template `.npmrc`: `install-links=true`.
- Scaffold copy: `packages/astro/` → `<project>/packages/astro/`; rewrite
  `file:../../packages/astro` → `file:packages/astro` in `package.json` and `package-lock.json`.
- Manifest path: `<site>/.astro/orso-content.json`.
- Manifest shape:
  ```json
  {
    "version": 1,
    "collections": [
      {
        "name": "blog",
        "loader": { "base": "src/content/blog/en", "pattern": "*.md" },
        "kind": "markdown",
        "singleton": null,
        "supportedForEditing": true,
        "reason": null,
        "fields": { "type": "object", "properties": {} }
      }
    ]
  }
  ```
- Endpoint: exact `POST /__orso`; JSON content type; loopback only; constant-time token comparison;
  no CORS; 2 MiB body limit.
- Endpoint token env var: `ORSO_CONTENT_TOKEN`, generated by the daemon per `start`, 32 random
  bytes hex-encoded.
- No npm publishing, no SSR adapter, no build-time manifest generation.
- Preserve existing source-preserving YAML/JSON behavior and existing API error reasons
  (`invalid_schema`, `unsupported_collection`, `stale_content`, `branch_changed`).

### Task 2: Schema description, manifest generation and atomic write

**Files:**
- Modify: `packages/astro/src/manifest.js`
- Modify: `packages/astro/src/index.js` (export the new helpers)
- Create: `packages/astro/test/fixtures/schemas.mjs`
- Test: `packages/astro/test/manifest.test.mjs`

**Interfaces:**
- `export function describeSchema(schema): object`
- `export function blocked(field): boolean`
- `export async function loadContent({ runner, configPath }): Promise<{ manifest, schemas }>`
  - `manifest` is `{ version: 1, collections: [...] }`.
  - `schemas` is a `Map<string, ZodType>`.
  - `runner` is an object with `import(path)`.
- `export function writeManifest(root, manifest): void`
- `export function isSupportedPattern(kind, pattern): boolean`
- `loadContent` must:
  - treat a missing `configPath` as an empty manifest;
  - import the module with `runner.import(configPath)`;
  - read `module.collections` as an object;
  - call a schema function with `{ image: () => z.string() }` from `astro/zod`;
  - run `describeSchema` and `blocked` to decide `supportedForEditing`;
  - keep a broken collection listed as read-only instead of failing the whole config;
  - throw only when the whole module cannot be imported or `collections` is not an object.
- `writeManifest` creates `.astro/`, writes a unique temporary file and renames it over
  `orso-content.json`; the JSON is pretty-printed with a trailing newline.

**Manifest entry rules:**
- `loader` is `{base, pattern}` only when the loader has `GLOB_META`; otherwise `null`.
- `kind` is the metadata kind, else `"unknown"`.
- `singleton` is the metadata singleton string or `null`.
- `fields` is the descriptor when a schema exists, else `null`.
- `supportedForEditing` is true only when:
  - the loader is `orsoGlob`;
  - the base is relative, non-empty, NUL-free and has no `..` component;
  - `isSupportedPattern(kind, pattern)` matches the Rust rules (`*.json`, exact `*.json` filename,
    `*.md`, `*.mdx` as applicable);
  - a schema exists;
  - no required field descriptor is blocked.
- `reason` is `null` for editable collections and a short explanation otherwise:
  - `"Collection does not use orsoGlob"`
  - `"Loader base must stay inside the project"`
  - `"Loader pattern is not supported for editing"`
  - `"Collection has no schema"`
  - `"Schema has required unsupported fields"`
  - `"Schema could not be inspected: <message>"`

**Fixture:** `test/fixtures/schemas.mjs` must mirror the template exactly: `blog` with
`title`, `description`, `pubDate`, optional `coverImage`/`coverAlt`, defaulted `tags` and
`relatedPosts`, the `coverAlt` super-refine and `.meta({ editor: { knownRefinement: true } })`;
`helpDocs` with `title`, `description`, `section`, `order`.

### Task 4: HTTP endpoint handler

**Files:**
- Create: `packages/astro/src/endpoint.js`
- Modify: `packages/astro/src/index.js` (export `createEndpoint`)
- Test: `packages/astro/test/endpoint.test.mjs`

**Interfaces:**
- `export function createEndpoint({ token, lookup })`
  - Returns a Connect/Vite middleware `(req, res, next)`.
  - `lookup(name)` returns `{ supportedForEditing, kind, schema, reason }` or `undefined`.
- Request:
  ```json
  { "op": "validate", "collection": "blog", "fields": {} }
  { "op": "patch", "collection": "blog", "source": "---\n...", "fields": {}, "unset": [], "body": "..." }
  ```
- Responses: exactly the shapes in the design spec. In particular:
  - `200 {"valid":true|false,"fields":{...},"errors":[...]}` for `validate`;
  - `200 {"source":"..."}` for `patch`;
  - `422 {"error":"invalid_schema","issues":[...]}`;
  - `400 {"error":"bad_request","message":"..."}`;
  - `401 {"error":"unauthorized"}`;
  - `404 {"error":"unsupported_collection","message":"..."}` for an absent collection;
  - `400` with the same error for a listed but unsupported collection;
  - `413` for body over 2 MiB;
  - `405` for non-POST;
  - `500 {"error":"internal","message":"..."}` for unexpected failures.
- The handler:
  - matches `new URL(req.url, "http://localhost").pathname === "/__orso"` exactly;
  - rejects non-loopback `req.socket.remoteAddress` when available (403);
  - requires `Content-Type: application/json` (parameters allowed);
  - reads the streamed body with a 2 MiB cap and rejects `Content-Length` over the cap;
  - compares the token with `crypto.timingSafeEqual` after a length check;
  - never logs the token and sends no CORS headers.

- [ ] **Step 1: Write the failing tests**

  Start a real `node:http` server around the handler and use `fetch`:
  - GET/PUT → 405;
  - text/plain → 400;
  - missing/wrong token → 401;
  - `Content-Length` > 2 MiB → 413;
  - `validate` valid → 200 with parsed/defaulted fields and empty errors;
  - `validate` invalid → 200 with `valid:false`, original fields and issue paths;
  - absent collection → 404;
  - `supportedForEditing:false` → 400 with the reason;
  - `patch` valid → 200 with a source string;
  - `patch` schema failure → 422 with packaged issues;
  - `patch` malformed/overlapping `unset`/unsafe source → 400.

- [ ] **Step 2: Run the test to confirm failure**

  ```sh
  npm --prefix packages/astro test -- --test-name-pattern="endpoint"
  ```

  Expected: FAIL because `src/endpoint.js` is missing.

- [ ] **Step 3: Implement the handler**

  Implement `MAX_BODY = 2 * 1024 * 1024`, `isLoopback(address)`, `readBody(req)`, `send(res,

  `SchemaIssuesError` to 422 and `PatchError` to 400. Catch unexpected errors, log only the

**Interfaces:**
- `orso()` returns an Astro integration named `orso-content`.
- `astro:config:done` stores `config`.

  - resolves `config.root` with `fileURLToPath`;

  - watches the content config and reloads on change;

    `runner.evaluatedModules.getModulesByFile(path)` and
    `runner.evaluatedModules.invalidateModule(module)` before re-importing;
  - on a whole-config import failure, logs the error and keeps the previous manifest and schemas;
  - on a per-collection loader/schema failure, writes that collection as read-only with the error
    reason; one broken collection does not hide the others.
- `orso()` is a no-op during build; manifest generation happens only through `astro:server:setup`

    pubDate: z.string().regex(/^\d{4}-\d{2}-\d{2}$/, "Use YYYY-MM-DD").refine((value) => {

    coverImage: image().meta({ editor: { type: "image" } }).optional(),
    coverAlt: z.string().optional(),
    tags: z.array(z.string()).default([]),
    relatedPosts: z.array(z.string().meta({ editor: { type: "reference", collection: "blog" } })).default([]),

    if (post.coverImage && !post.coverAlt?.trim()) {

### Type and naming consistency

- `ContentEndpoint` lives in `src/content/integration.rs`; `AppState` imports it; tests construct it
  only through `AppState::content_endpoint`.
- The JavaScript package exports only `orso`, `orsoGlob` and the testable helpers; the production
  integration uses `loadContent`, `writeManifest` and `createEndpoint` internally.
- Rust `ContentCollection` keeps `loader`, `kind`, `singleton`, `editable`,
  `supportedForEditing`, `reason`, `fields`; the manifest JSON names match the existing serde
  rename.
- `patch` keeps the current argument order for `source`, `fields`, `unset`, `body`; only the
  endpoint resolution moves outside it.
- `PREVIEW_REASON` and `PREVIEW_SAVE_REASON` are single-sourced constants used by the HTTP overlay
  and the save/lifecycle failures.

### Failure modes checked

- Missing/malformed manifest: empty list, no fallback, reading unavailable; Task 8 tests.
- Config load failure: previous manifest/schemas remain; Task 5 implementation.
- First manifest write awaited before ready; Task 5 and Task 16 E2E.
- No token/not ready: read-only overlay and `DEVSERVER_ERR` save; Task 13 tests.
- Token rejected: client maps to `DEVSERVER_ERR`, no retry; Task 11.
- Schema failure: 422 with issues; no writes; Tasks 11 and 13.
- Source-preservation refusal: 400; no writes; Tasks 3, 4 and 13.
- Endpoint dies mid-save: save fails, journal/recheck keep files unchanged; existing mutation tests
  plus Task 13.
- Config-change race: manifest watcher/reload + Content store refresh; Tasks 5, 9 and 15.
- Scaffold path rewrite: `npm ci` test; Task 16.

### Deliberate boundaries

- No editor field-shape changes; manifest fields reuse `FieldDescriptor`.
- No arbitrary loader support; non-`orsoGlob` loaders are listed read-only with `loader:null`.
- No manifest during `astro build`; `astro sync` and dev only.
- No npm publishing.
- No automatic integration for imported/cloned non-template projects.
- The real Astro E2E remains ignored for normal test runs because it needs network and npm, matching
  the existing scaffold install/build test.

### Verified assumptions

- Astro 7.3.5's `astro sync` creates a temporary Vite server and runs `astro:server:setup`;
  `server.environments.astro.runner` is available there.
- Vite's runner exposes `runner.evaluatedModules.getModulesByFile(file)` and
  `invalidateModule(module)`; the integration uses those before re-importing the content config.
  If a future Astro/Vite upgrade removes them, use a cache-busting query on `runner.import` while
  preserving the same reload behavior.
- The package's generated lockfile path rewrite is guarded by the Task 6 extraction test and the
  Task 16 scaffold `npm ci` test; if either finds a path key the string rewrite misses, update the
  rewrite to cover it.
